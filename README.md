# k8s-cert-lab

A reproducible [`kind`](https://kind.sigs.k8s.io/)-based lab for practicing
CKA, CKAD, and CKS troubleshooting. Every scenario provisions a Kubernetes
cluster into a deliberately broken state, gives you a fixed time budget to
diagnose and fix it, and then checks your work with a script — not by eye.

This repo is the base for a daily YouTube series working through the
[CNCF exam curricula](https://github.com/cncf/curriculum) one scenario at a
time.

## Safety — read this before running anything

These scripts intentionally break Kubernetes clusters on purpose. That is
the point of the lab, but it means every script here must never be able to
touch a real cluster.

- `lib/guard.sh` is sourced by every mutating script. It refuses to run
  unless the active `kubectl` context is `kind-<profile>` for a profile in
  `lib/guard.sh`'s `ALLOWED_PROFILES` (`solo trio nocni hardened etcdlab`),
  and it never reads or writes `~/.kube/config` — each profile gets its own
  kubeconfig at `.work/kubeconfig-<profile>`.
- **Never point any script in this repo at a real cluster.** If you adapt
  these scenarios elsewhere, keep the guard, or add an equivalent context
  check, before running anything that mutates cluster state.

## Quickstart

```bash
bin/doctor.sh                                   # checks host tooling versions and limits
bin/scenario.sh setup  cka-tshoot-pending-pods   # brings up the right profile, breaks it
# ... diagnose and fix it using kubectl against the printed kubeconfig ...
bin/scenario.sh verify cka-tshoot-pending-pods   # checks your fix, non-zero if it's wrong
bin/scenario.sh solve  cka-tshoot-pending-pods   # applies the reference solution, if you're stuck
```

Each scenario's own `README.md` (for example
[`scenarios/cka-tshoot-pending-pods/README.md`](scenarios/cka-tshoot-pending-pods/README.md))
has the task statement and a full walkthrough.

## Host requirements

- [`kind`](https://kind.sigs.k8s.io/) >= v0.32.0
- Docker, with the daemon reachable from your user
- >= 8 GiB free disk (the default `LAB_MIN_DISK_GIB` floor, checked and
  documented in `bin/preflight.sh`; derived from measured usage — cached
  node images 0.9 GiB, a running `trio` adds ~2 GiB of writable layers)
- `fs.inotify.max_user_instances` >= 512 (multi-node clusters fail with
  "too many open files" below this; `max_user_watches` needs no change)

Run `bin/doctor.sh` to check all of the above, plus `helm`, `shellcheck`,
`yq`, `jq`, and `kubectl`, against the versions this repo depends on.

## Profiles

Each profile is a `kind` cluster config in `profiles/`, selected per
scenario by that scenario's `meta.yaml`. Node images are pinned by digest,
never by a floating tag.

| Profile | Nodes | Purpose |
|---|---|---|
| `solo` | 1 control-plane | Single-node scenarios — fastest to bring up |
| `trio` | 1 control-plane + 2 workers | Scheduling, affinity, and multi-node troubleshooting |
| `nocni` | 1 control-plane + 1 worker, no CNI | Networking scenarios that start with nodes `NotReady` until a CNI is installed |
| `hardened` | 1 control-plane, audit logging + encryption-at-rest configured | CKS scenarios needing audit policy or Secret encryption |
| `etcdlab` | 1 control-plane, `etcd-backup` host mount | etcd backup/restore scenarios |

Bring a profile up or down directly with `bin/cluster.sh <up|down|status> <profile>`.
Only one cluster runs at a time.

## The scenario contract

Every directory under `scenarios/<slug>/` provides exactly these files, and
`tests/scenario.bats` enforces that they exist:

- `meta.yaml` — `slug`, `title`, `profile`, `cert`, `curriculum_version`,
  `domain`, `domain_weight`, `difficulty`, `time_budget_minutes`,
  `namespace`, `attribution`
- `setup.sh` — brings the cluster into the broken state
- `verify.sh` — exits 0 only if the task is correctly solved
- `solve.sh` — applies the reference solution
- `README.md` — the task statement and a full walkthrough

All three scripts source `lib/guard.sh` and call `kubectl` only through its
`kc` wrapper, which re-asserts the expected context on every single call.
`bin/scenario.sh <setup|verify|solve|reset> <slug>` is the only supported
entry point — it reads the scenario's `profile` from `meta.yaml`, brings
that profile up if needed, and then runs the requested phase.

## Curriculum coverage

[`docs/curriculum-map.md`](docs/curriculum-map.md), generated by
`bin/coverage.sh`, tracks which CKA v1.35 and CKS v1.34 domains have a
scenario and which are still a gap. Right now there is exactly one
scenario (`cka-tshoot-pending-pods`, CKA Troubleshooting), so every other
domain is a `GAP` — that gap list is the episode backlog.
